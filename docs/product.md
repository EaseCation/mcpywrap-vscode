# 产品场景与需求

## 1. 产品目标

让开发者在代码工作区完成一次完整测试循环：选择项目与世界、运行、观察、执行诊断代码、更新模块、继续测试、明确结束。降低切换工具与选错会话的成本，同时复用 mcpy 的项目和运行管理能力。

插件是 mcpy 的独立客户端。mcpy 无需知道 VS Code 是否存在，插件也不拥有引擎安装、构建装配、部署与锁管理。用户离开 VS Code 后，仍可用 CLI 管理同一游戏。

## 2. 用户与任务

| 场景 | 起点与目标 | 成功体验 | 约束 |
| --- | --- | --- | --- |
| S1 新项目首次测试 | 已由 mcpy 初始化的项目，尚无世界 | 选择新建世界，看到准备进度和实际启动结果 | 环境缺失时给出诊断；不自动修改依赖或配置 |
| S2 日常迭代 | 已有世界，希望保留进度 | 运行所选世界，看日志，热更指定模块 | 复用已有进程不表示部署了新代码 |
| S3 Python 诊断 | 光标位于业务 Python 文件 | 选区执行到选定会话和端侧，看到输出与异常 | 游戏解释器与宿主 Python 分开；不自动重复执行 |
| S4 双客户端联调 | 一个项目、两个玩家 | 显示组与成员，明确客机等待加入、组热更和整组停止 | 客机手动加入状态不算失败；外服不开放 server 执行 |
| S5 多项目并行 | 多根工作区或一个工作区内多个项目 | 自动识别嵌套项目，编辑器右上角提供当前文件所属项目入口，不把操作发到另一个项目 | 路径、会话、端侧一起确定目标 |
| S6 故障与恢复 | CLI 丢失、响应超时、编辑器重载 | 能区分未提交与结果未知，刷新找回会话 | 不从超时推导“游戏没启动”，不自动重发 |
| S7 运行时断点 | 需要定位真实业务回调 | F5/附加、断点、调用栈、局部变量与继续闭环 | 后续阶段；需要 mcpy 通用调试能力与后端实证 |

核心用户是已使用 mcpy 的 Mod/Addon 开发者；熟悉 CLI 的用户能用相同术语操作。首次接触者依靠空状态、动作说明和环境诊断完成引导。

## 3. 需求优先级

P0：独立项目与发布边界、公开 CLI 单向调用、项目/会话选择、启动/停止、日志快照、执行选区、模块热更、多项目隔离、失败语义和进程归属交给 mcpy。

P1：自动热更任务、连续日志 cursor、项目脚本入口、世界参数表单、自动恢复已选目标、结构化诊断与测试函数。

P2：通用 DAP 端点接入、已验证平台上的断点、Test Explorer、UI 调试及截图工具。

P0 的完成不宣称 P1/P2 已可用。CLI 尚无公开能力时记录能力缺口；不使用私有实现绕过。

## 4. 交互原则

1. **目标先于动作。** 会话选择显示项目、世界/角色和状态；执行前显示 client/server。
2. **动作与效果分开。** 进程运行、脚本就绪、请求执行完成、玩法效果验证分别呈现。
3. **保留用户上下文。** 保留存档进度与游戏，关闭面板不会停止会话；失效目标要求重新选择。
4. **渐进呈现。** 首先展示运行与日志；选中会话后开放运行时动作；没有支持证据的功能不伪装成可用。
5. **恢复优先。** 错误保留 code/hint、会话和端侧；未知结果引导查询，不给“再试一次”默认动作。
6. **沿用 VS Code。** 原生 TreeView、QuickPick、Output、进度与设置；复杂信息达到需要时才引入 Webview。
7. **配置单一来源。** 项目业务配置仍属于 mcpy；插件设置仅含 CLI 路径与等待偏好；项目根由声明自动发现。

## 5. 可观察的产品质量

启动不阻塞 Extension Host；每项目避免重复变更操作；状态查询失败保留上次列表并标记过期；日志快照明确采样时间；不根据文件名猜端侧；不自动扫描用户整个磁盘；未知字段可兼容，关键字段缺失则停止该动作。

阶段验收使用场景编号关联测试。真实游戏与断点验证必须补充引擎、平台、端侧和实际效果，不能用 mock 通过替代。
